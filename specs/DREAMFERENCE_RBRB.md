# RBRB: the Ragon-Builds-Ragon benchmark

**Status:** decided, **built in part**. Only the `Made-with: ragon` trailer is on `main` (`scripts/as_team.py commit … --made-with ragon`, §14). Everything else here is specified and not yet built: the `Ragon-Tokens` trailer, the job tag on Ragon's requests, the private ledger, the routing rule, the ratchet, `scripts/rbrb.py`, `docs/rbrb.json`, `images/rbrb.svg`, the README section and the weekly workflow. §2–§9 are normative. The numbers in the examples are illustrative unless they are marked as measured.
**Names:** the programme and its curve are the **Ragon-Builds-Ragon benchmark**, short **RBRB**. The files are `scripts/rbrb.py`, `docs/rbrb.json`, `images/rbrb.svg`, and the ledger is `rbrb.jsonl`.
**Builds on:**
- [ORGANISATION](./DREAMFERENCE_ORGANISATION.md): the team bots and `scripts/as_team.py`, the only way commits are made as a team, and its message guard.
- [PYTHON_QUALITY](./DREAMFERENCE_PYTHON_QUALITY.md): the code-standard ratchet that every change passes.
- Ragon's `task` tool (`ragon-rs/delegate/src/task.rs`): the bounded edit with one acceptance test, and its own ledger of verdicts.
- The model gate (`vllm_server/model_gate_service.py`) and its `client_metadata` rules ([docs/dev/loop-guard.md](../docs/dev/loop-guard.md)): the place where Ragon's tokens are counted per request.

---

## 0. Decisions, stated first

1. **Quality first, progress second** (the owner, 2026-11-12, verbatim: "It is incredibly important that as we increase RBRB the quality should be not affected. Quality first, progress second."). Every rule below is subject to this one. When the quality condition (§2.7) fails, the target stops rising and routing steps back (§6, §11). There is no rule that trades quality for share.
2. **The curve is in tokens.** RBRB for an ISO week is the share of development tokens that Ragon generated, against the tokens generated by any other model.
   - **Primary measure:** generated (completion) tokens on both sides. Cache-read tokens would swamp a ratio of total tokens.
   - **Secondary measures:** prompt and cache tokens are recorded and shown as a secondary line.
3. **Other models are never named.** The other side is "other models" in every commit, in the chart, in the README and in this repository. Ragon is the only tool that is ever named (§8).
4. **Every commit says what Ragon spent on it.** Every commit the coordinator lands carries `Ragon-Tokens: <n>`, and `0` is allowed. This holds even when another model drove the change. A commit whose change Ragon made also carries `Made-with: ragon` (§3).
5. **Both groups pass the same gates.** Ragon's commits and all other commits pass the same tests and the same reviews (§9). Ragon's work has extra checks of its own, and never fewer than the others'.
6. **The public curve shows only what landed.** Every attempt is recorded in a private ledger (§4). Commits and lines count only landed commits. Tokens are the week's development tokens on both sides; §10 says what that means.
7. **The target is private.** The weekly target share lives in the coordinator's configuration, never in a repository, and it only rises (§6).
8. **The public numbers come from the repository alone.** `scripts/rbrb.py` reads the git history and the committed input rows of `docs/rbrb.json`, and writes the rest of the file and the chart. It is deterministic and uses no network (§7).
9. **Baseline: 0 % on 2026-11-12.** History before that date counts as 0. The first point (week 2026-W46, measured by hand, `method_version` 0) is the one exception, recorded with its limits (§7.1).

## 1. Purpose, and the owner's words

The owner, 2026-11-12:

> "I want to gradually move development to ragon: essentially you will be passing more and more work to ragon without compromising quality. This may take a long, long time. But I want to start tracking this as a curve and make the curve public on the README."

Then, the same morning: **"Quality first, progress second."**

**Why a benchmark.** Ragon is a coding agent with a local model. The most demanding codebase it can be measured on is its own:
- the inference engine;
- the agent and its patches;
- the installers, the desktop app and the phone bridges;
- the specs and the tests.

RBRB measures how much of that work Ragon does itself, week by week, under the same gates as everything else. Expect a curve that starts near zero and rises slowly over a long time. A curve that rises while quality falls is a failure of the programme, not a success.

**What it is not.** It is not a SWE-bench-style score of solved tasks ([RAGON_SWE_BENCH](./DREAMFERENCE_RAGON_SWE_BENCH.md) is that). It is not a promise about any date.

## 2. Definitions

### 2.1 A development token

A token generated or read by a model on work for this repository or its engine, attributed to a coordinator job.

| | Ragon side | Other side |
|---|---|---|
| **Source** | The model gate's per-request usage counters on the node (§4.3). Only requests that carry a job tag count. | The coordinator's per-job usage ledger. It covers the coordinator's own session and every worker session it dispatched. |
| **What it counts** | Requests from `ragon exec` and from Ragon's `task` tool under a coordinator job. | Every model other than Ragon. |

**Excluded on both sides:**
- benchmark nights (SWE-bench and the engine's measurement runs);
- the morning QA passes;
- Night Shift tasks of the product itself;
- any request without a job tag.

### 2.2 The share (RBRB)

For an ISO week `w`, the primary share is computed from generated tokens:

```
rbrb_share(w) = ragon_generated(w) / (ragon_generated(w) + other_generated(w))
```

The value is `0` when both counts are 0. It is rounded to four decimals in `docs/rbrb.json` and shown as a percentage with two decimals.

The **secondary token share** is the same ratio over `generated + prompt + cached` tokens on both sides.

### 2.3 A Ragon-made commit

A commit on `main` whose message ends with the trailer `Made-with: ragon` (§3).

**When the trailer is allowed:** only when the committed diff is the diff a Ragon task returned. Two edits are allowed beside it:
- the commit message;
- a rebase that changes nothing but context lines.

**When it is not allowed:** a change in which any other model or a person edited a line of Ragon's diff is not Ragon-made. It is counted on the other side. Its `Ragon-Tokens` still records what Ragon spent on it. **Rule: when in doubt, leave the trailer off.**

### 2.4 A week

An ISO-8601 week, Monday 00:00 to Sunday 24:00 UTC, written `2026-W46`.
- **Commits:** a commit belongs to the week of its committer date. The land queue sets that date in UTC when it rebases.
- **Tokens:** a token belongs to the week of its request's end.

### 2.5 A revert

A commit `X` on `main` counts as reverted when a later commit on `main` contains the line `This reverts commit <full sha of X>.`. That is the line `git revert` writes.

- **Which week it counts in:** the week in which `X` landed.
- **Window:** a revert counts only within 28 days of `X` landing. The four newest weeks of revert rates are therefore provisional, and the JSON marks them `"provisional": true`.
- **Fix-ups:** a fix-up that is not a `git revert` is not a revert. The private ledger records it (`reason: "fixup"`, §4) so that the owner can see it.

**Revert rate of a group:** reverted commits of the group, divided by all commits of the group in the window.

### 2.6 A land-test failure

A land attempt whose test (`--test` of the land queue, run on the commit after it is rebased onto `main`) failed, so that nothing was pushed. Each attempt is counted once, and its retries count as attempts of their own.

**Failure rate of a group:** failed attempts divided by all attempts of the group in the week. The land queue's journal is the source, and it is private. The weekly counts are published as committed input rows (§7.1).

### 2.7 The share of commits and of lines (secondary)

- **Commit share:** Ragon-made commits on `main` (first parent, no merge commits) in the week, divided by all such commits.
- **Line share:** the lines added plus the lines deleted (`git log --numstat`) of Ragon-made commits, divided by the same count for all commits.

**Excluded from both counts:**
- the weekly RBRB commit itself;
- generated files: `docs/rbrb.json`, `images/rbrb.svg`, `tests/typing_baseline.json`, lockfiles, and binary files (numstat `-`).

### 2.8 The quality band

The quality condition holds for a trailing window of eight completed weeks when all three of these hold:
1. Ragon's revert rate is **at or below** the revert rate of all other commits.
2. No Ragon-made commit was landed past a gate (§9). A bypass is a failure whatever the rates say.
3. There are at least **20** Ragon-made commits in the window. The figure is the `task` tool's own `MIN_DECIDED`.

With fewer than 20, the band is **undecided**, and an undecided band acts as a failed one for the ratchet (§6). The JSON records the band as `"met"`, `"failed"` or `"undecided"`.

## 3. The trailers

### 3.1 Format

Two git trailers form the last paragraph of the message. They follow one blank line, in this order:

```
<subject>

<body>

Ragon-Tokens: <n>
Made-with: ragon
```

| Trailer | Form | When present |
|---|---|---|
| `Ragon-Tokens` | A decimal integer `n ≥ 0`: the tokens Ragon generated on this change, with no sign, no separators and no unit | Required on every commit the coordinator lands, from the entry of phase 0 (§11) |
| `Made-with` | The value `ragon`, exactly | Only on a Ragon-made commit (§2.3) |

**How `n` is counted:** it is the sum of `generated` over every ledger row of the job that produced this commit (§4), including attempts that failed before a fallback. A job that lands several commits splits its tokens across them by the ledger rows' `sha`. Rows with no sha go to the job's last commit.

**Reading the trailers:** `git interpret-trailers --parse` reads them. A reader takes the **last** value of each key.

### 3.2 Where they are added

- **`scripts/as_team.py commit <team> -m MSG --ragon-tokens N [--made-with ragon]`:**
  - built: `--made-with`;
  - specified: `--ragon-tokens`.
  The job's `N` comes from the ledger (§4) for its job id. The coordinator's land wrapper passes it and never types it by hand.
- **The land queue:** it does not add trailers. It refuses (§3.3).
- **The weekly workflow (§7.4):** its commit carries `Ragon-Tokens: 0`.

### 3.3 What refuses a trailer

| Where | It refuses |
|---|---|
| `as_team.py commit` | Any `--made-with` value other than `ragon` (built). A `--ragon-tokens` value that is not a decimal integer `≥ 0` (specified). |
| The land queue, from phase 0 | A commit that has no `Ragon-Tokens`. A commit with more than one `Made-with`. A commit with `Made-with: ragon` but `Ragon-Tokens: 0`: Ragon made it, so it spent tokens. |
| The message guard (`MessageGuard`, `as_team.py`) | Any message that names a denylisted tool, person or host, as it does today. The guard strips co-author and session trailers and "Generated with/by" lines. It does **not** strip `Ragon-Tokens` or `Made-with`, and a test keeps it so (§12). |

### 3.4 Idempotence

- **Re-running `commit`:** with the same flags on a message that already ends in the block, nothing is added. With a different `N`, the value is **replaced**, never duplicated, and the order stays `Ragon-Tokens` then `Made-with`.
- **Rebases and replays:** a land-queue rebase keeps messages verbatim. So do `as_team.py publish` (both modes) and a cherry-pick.
- **Squash merges:** they are not a landing path (landing is a fast-forward). A squash merge done by hand must carry the block of the squashed commits: the sum of their `Ragon-Tokens`, and `Made-with: ragon` only if every squashed commit had it.

### 3.5 Examples

These examples are illustrative.

Another model drove the change, and Ragon was not used:

```
docs: the release spec's install section names the signed tarball

Ragon-Tokens: 0
```

A Ragon task made the change, it passed, and it landed:

```
tests: cover the empty-folder case of the docs index

The acceptance test was tests/test_docs_index.py::test_an_empty_collection_indexes_nothing.

Ragon-Tokens: 14212
Made-with: ragon
```

A Ragon task failed twice and the change was then made on the other path. The commit is not Ragon-made, and Ragon's spend is still recorded:

```
web: the upload cap is read from the policy file

Ragon-Tokens: 31877
```

## 4. The ledger (private)

### 4.1 Where it lives

`rbrb.jsonl` sits in the coordinator's state folder on the coordinator's machine.

- **Never in a repository**, never pushed, never published.
- **Append-only:** one JSON object per line, in UTF-8.
- **No content:** no brief text, no code, no model output, and no names. This follows the `task` tool's own ledger (`ragon-rs/delegate/src/task.rs`, `Ledger`), which it complements: that ledger records a task's verification and verdict; this one records the attempt's place in the programme.

### 4.2 Schema (version 1)

| Field | Type | Meaning |
|---|---|---|
| `v` | int | Schema version, `1` |
| `id` | string | Row id, `<job id>-<n>`, where `n` counts from 1 within the job |
| `job` | string | The coordinator job id; the same value as the request tag (§4.3) |
| `repo` | string | `ragon` or `ragon-engine` |
| `kind` | string | `mechanical`, `docs`, `tests`, `code` or `feature` (§5.1) |
| `class` | string or null | The `task` tool's class (`T1`…`T5`) when a task ran |
| `started`, `finished` | string | RFC 3339, UTC, to the second |
| `outcome` | string | `landed`: Ragon's diff landed and the commit is Ragon-made. `failed`: nothing landed. `fallback`: Ragon's attempt failed and the change landed on the other path. |
| `reason` | string or null | For `failed` and `fallback`: `verification`, `test`, `too_large`, `timeout`, `review_reject`, `land_test`, `window` (no attempt: night hours or a GPU window), `fixup` (a later fix-up of a landed row) |
| `test` | string or null | The one acceptance test, as a pytest node id or a `cargo test` filter |
| `sha` | string or null | The landed commit, when there is one (`landed`, `fallback`) |
| `ragon_generated`, `ragon_prompt`, `ragon_cached` | int | Ragon's tokens for this attempt, read from the gate's counters by job tag and time window |

Example (illustrative):

```json
{"v":1,"id":"b-docs-index-empty-1","job":"b-docs-index-empty","repo":"ragon","kind":"tests","class":"T2","started":"2026-11-16T10:02:11Z","finished":"2026-11-16T10:19:40Z","outcome":"landed","reason":null,"test":"tests/test_docs_index.py::test_an_empty_collection_indexes_nothing","sha":"<40 hex>","ragon_generated":14212,"ragon_prompt":88410,"ragon_cached":61002}
```

### 4.3 The Ragon side's counters

The counters are specified here and not yet built.

1. **The tag.** The launcher puts `ragon_job` into `client_metadata` when `DREAMFERENCE_RAGON_JOB` is set. It goes beside `ragon_surface` and `ragon_workload`, where the extension API puts them ([docs/dev/loop-guard.md](../docs/dev/loop-guard.md)). `ragon exec` and the `task` tool pass the coordinator's job id through it.
2. **The count.** The model gate appends one line per finished request to its usage log in the gate's state folder on the node. The line holds the end time, the job tag, and the prompt, cached and generated tokens from the engine's usage block.
3. **What is skipped.** Requests without a tag are counted in the engine's totals but not here. So are requests whose workload is `swe-bench` or `night`.
4. **Privacy.** The usage log holds no content, only numbers and the tag.

### 4.4 Retention

- **Rows are kept.** They are small and hold no content, and keeping them lets the public curve be re-derived and audited.
- **Yearly split.** In the first week of each year, the previous year's rows move to `rbrb-<year>.jsonl` beside the ledger.
- **The gate's usage log** is kept for 90 days. The weekly export (§7.1) is its only reader.

## 5. Routing and fallback

### 5.1 Which work goes to Ragon first

| Kind | What it covers | Ragon first from |
|---|---|---|
| `mechanical` | A rename, formatting, a lint or typing fix, a version bump, a moved constant | Phase 1 |
| `docs` | `docs/`, `specs/` edits that follow a decided text, README lines, docstrings | Phase 1 |
| `tests` | A new test or a test for a found bug, in the `task` tool's test class (`T2`, which may not delete an assertion without replacing it) | Phase 1 |
| `code` | A change of behaviour with a named test that fails before and passes after | Phase 2 |
| `feature` | A feature from a spec, split into tasks that each meet the bound | Phase 3 |

**Never routed to Ragon first, in any phase:**
- security fixes;
- signing and release keys;
- changes to the gates themselves (§9);
- the merge of a release;
- anything a brief marks `owner-only`.

### 5.2 The bound on a Ragon task

A Ragon task is one call of the `task` tool, with the limits it enforces itself (`ragon-rs/delegate/src/task.rs`):

| Limit | Value |
|---|---|
| Files | The files that may change, listed up front: at most 20 (`MAX_FILES`). A change outside the list is reverted and fails the task. |
| Steps | At most 20 steps (`MAX_STEPS`). |
| Acceptance test | Exactly **one**. |
| Size | The class's changed-line limit (`size_limit`: 400 for `T1` and `T3`, 150 for the others). |
| Diff returned | At most 20,000 characters (`MAX_DIFF_CHARS`); a larger one fails as `too_large`. |
| Run time | 1,500 s by default and at most 3,600 s (`DEFAULT_AGENT_TIMEOUT_S`, `MAX_AGENT_TIMEOUT_S`). |
| Commits | None. The tool never commits; the caller reviews the diff and commits it with the trailers. |

**When it runs:** the coordinator's rules allow a task from 08:00 to 20:30 UTC, and never while the model server is stopped for a GPU window. Outside those hours the attempt is skipped and recorded as `fallback` with `reason: "window"`.

### 5.3 When the fallback happens

After the **first** failed attempt, the job may retry **once**, with the failure's tail added to the brief. The other path takes over after the second failure. Any of these counts as a failure:
- the tool's own checks fail (`verification`, `too_large`);
- the acceptance test fails;
- the run time is exceeded;
- the reviewer of the diff rejects it;
- the land test fails on the rebased commit.

A `review_reject` is never retried with the same brief: the brief was wrong or the task too big.

### 5.4 How a fallback is counted

- **In the ledger:** each attempt is a row. The last row of a fallback has `outcome: "fallback"` and the sha of the commit that landed.
- **In the commit:** it has no `Made-with`. Its `Ragon-Tokens` is the sum of Ragon's tokens over all of the job's attempts (§3.1). So the tokens Ragon spent on a failure are visible on the commit but never count as a Ragon-made commit.
- **In the public curve:** it counts on the other side for commits and lines. Its Ragon tokens stay in the week's Ragon token total (§10).
- **Privately:** each week the coordinator reads the ledger's attempted, landed, failed and fallback counts per kind. A kind whose landed-to-attempted ratio stays under 50 % for four weeks is reviewed: either its briefs change or the kind goes back to the previous phase.

## 6. The ratchet

### 6.1 The rule

The target `T(w)` is the share the coordinator aims for in week `w`. It is recomputed every Monday for the new week:

```
S4(w)  = rbrb_share over the four completed weeks before w (tokens summed, then divided)
T(w)   = T(w-1)                                   if the quality band (§2.8) is not "met"
T(w)   = max(T(w-1), min(S4(w), T(w-1) + Δ))      if it is "met"
T(first week) = 0
```

- **It never falls.** The target stays where it is when the band fails or is undecided.
- **It follows what was achieved.** It rises at most `Δ` a week, and never above what Ragon actually achieved over four weeks.
- **`Δ`:** the default is 2 percentage points (open question 5).

### 6.2 Cadence

Every Monday at 06:00 UTC, after the ISO week closes, the coordinator does three things:
- reads the ledger and the gate's usage logs;
- writes the week's input row (§7.1);
- computes `T`.

A week whose share falls below its target is a **miss**. The weekly note names the reason (no suitable work, failures, a GPU window). A miss never lowers the target.

### 6.3 Who changes the target

Only the owner. `T`, `Δ` and the band's thresholds live in the coordinator's configuration, never in a repository, and the coordinator applies the formula. A change by hand is recorded in the coordinator's decision log with the reason.

### 6.4 The quality condition comes first

The target exists to push work to Ragon. When the band is `failed`, three things happen:
- the target freezes;
- routing of the kinds that produced the reverted commits steps back one phase (§11);
- the reverted commits are reviewed before any of those kinds is routed to Ragon again.

**Quality first, progress second.**

### 7.2 `images/rbrb.svg`

The chart is plain SVG text that `scripts/rbrb.py` writes, with no third-party package. It is byte-identical for the same inputs: fixed number formatting, no timestamp, and no random ids.

| Element | What it shows |
|---|---|
| x axis | ISO weeks from the baseline to the newest point |
| y axis | Share in percent, 0–100: the honest scale, so the distance still to go is visible |
| Solid line with points | `rbrb_share`, generated tokens |
| Dashed line | `secondary_share`, all tokens |
| Dotted line | The commit share (§2.7) |
| Text, top right | The newest value with its week, e.g. "2026-W47: 1.75 %" |
| Text, beneath | Ragon's revert rate against the others' over the eight-week window, with counts ("0 of 6 against 5 of 402"), and the band |
| Caption | "generated tokens by Ragon as a share of all development tokens, per week" |

**What it never shows:**
- the target;
- any model's or tool's name other than Ragon's;
- any person, host or job id.

**Colours:** two theme-neutral colours that read in light and dark README themes.

### 7.3 The README section

The section sits after the main feature sections and before "Star history". Its title is **"RBRB: the Ragon-Builds-Ragon benchmark"**, and it holds one paragraph, the chart and the current numbers. The proposed text, verbatim (the bracketed values are filled from `docs/rbrb.json` by `scripts/rbrb.py`, between marker comments, so the numbers never drift from the file):

> Ragon is being built more and more by Ragon. Every week we measure the share of the tokens spent on developing Ragon that Ragon's own local model generated, against the tokens of every other model we use; every commit records the Ragon tokens it took. Ragon's changes pass exactly the same tests and reviews as every other change, and we track how often they are reverted beside the curve: quality first, progress second. The curve started at zero on 12 November 2026 and is meant to rise slowly, over years, never by lowering the bar.
>
> ![RBRB](images/rbrb.svg)
>
> **Latest:** [week] — [share] % of generated tokens; Ragon's revert rate [k of n] against [k of n] for the rest.

### 7.4 The weekly workflow

`.github/workflows/rbrb.yml` regenerates the derived fields, the chart and the README numbers.

**Triggers:**
- `schedule`, Mondays at 07:00 UTC, after the coordinator's 06:00 input commit;
- `workflow_dispatch`.

**What it does:**
1. It checks out `main` with full history (`fetch-depth: 0`).
2. It runs `python scripts/rbrb.py`, which uses only the standard library and no network.
3. If anything changed, it commits **only** `docs/rbrb.json`, `images/rbrb.svg` and the README's marked block, as the **docs team bot** (`dreamference-docs[bot]`). The message is `docs: RBRB for <week>`, with `Ragon-Tokens: 0`.
4. It pushes to `main` as a fast-forward.

**What it refuses:**
- a diff outside those three places;
- a run on any branch but `main`.

**What it cannot do:** it never writes input fields, because it has no access to the private sources. Credentials are open question 2.

## 8. Privacy and naming

1. **Ragon is the only tool named.** No commit message, trailer, chart, JSON field, README text or spec section of this programme names any model, agent or tool other than Ragon. The other side is "other models", and its tokens are one number per week.
2. **No person.** No name, user name or account appears in any artefact. Commits are made as team bots, dated in UTC.
3. **No host.** No hostname, IP address, home path or node name appears in the public artefacts. The "node" and "the coordinator's machine" stay unnamed.
4. **No job ids in public.** Job ids appear only in the private ledger and in the gate's usage log.
5. **The private parts stay private.** The ledger, the gate's usage logs, the land queue's journal, the coordinator's usage ledger and the target never leave the coordinator's machine and the node. They are published only as weekly totals.
6. **Enforced.** The message guard's denylists, which are kept outside the repository so that they never name what they forbid, check every commit message the bots send. The naming test (§12) checks the generated artefacts.

## 9. The quality gates that apply equally

Every commit, Ragon-made or not, passes all of these. None is relaxed for either group, and a gate is changed only by the owner.

| Gate | Where | What it does |
|---|---|---|
| **The land queue's test run** | The coordinator's land queue (no repository pointer) | Runs the job's `--test` on the commit after it is rebased onto `main`. A failure stops the push (§2.6). Landing is a fast-forward only, never a force push, and pre-push hooks run. |
| **The test suite** | `tests/`, `AGENTS.md` "Commands" | The whole suite runs in CI and before a release. |
| **The ratchet tests** | `tests/test_code_quality.py`, `tests/test_typing.py` (baseline `tests/typing_baseline.json`); [PYTHON_QUALITY](./DREAMFERENCE_PYTHON_QUALITY.md) | No ruff or mypy count rises above its baseline. |
| **The default-flip reviewer** | The coordinator (a separate review job, no repository pointer) | Before a commit that changes a default (a knob on or off, a checkpoint, a pinned engine) is published, it re-reads the identity gates against the report and checks the diff for anything beyond the flip. It answers GO or STOP, and STOP holds the commit. |
| **The team review gate** | `scripts/as_team.py gate`, the `team-review` status; [ORGANISATION](./DREAMFERENCE_ORGANISATION.md) §5–§6 | Pull requests need the owning team's review. |
| **CI on `main`** | `.github/workflows/` (`rust-lint.yml`, `windows.yml`, `release-dry-run.yml`, …) | A red run on a commit is fixed or reverted. |
| **The message guard and the anonymity hook** | `MessageGuard` in `scripts/as_team.py`; the pre-push hook | No commit names a denylisted tool, person or host. |
| **The hard rules** | `AGENTS.md` "Gotchas: the hard rules" | For example, tests never touch the real machine. |

**Ragon's extra checks.** These come before the gates above and are never instead of them:
- the `task` tool's own checks: the listed files only, the size limit, the one acceptance test and ruff on touched Python. They are run by the tool itself, which never trusts the agent's word.
- the review of the returned diff against its brief (accept or reject), which is recorded in the `task` tool's ledger.

## 10. What the curve can and cannot show

**It can show:**
- the share of the week's development tokens that Ragon generated;
- beside that, the share of landed commits and lines that Ragon made;
- whether Ragon's commits are reverted more often than the rest.

**It cannot show the following, and the README and the chart do not claim it:**

1. **Tokens measure effort, not value.** A model that writes more words for the same change gets a bigger share. **Ragon's failed attempts raise the token share**: their tokens count in the week's Ragon total, even though the change then lands on the other side. Two figures keep this honest:
   - `landed_ragon_tokens`, the sum of the trailers on landed commits;
   - the commit share, which counts landed work only.
2. **Different tokenizers.** Ragon's model and the other models split text into tokens differently, so a token is not the same unit on both sides. The ratio is a trend, not an exact split of the work.
3. **The other side is a lower bound for now.** Until every worker session is in the coordinator's usage ledger, the other side is undercounted. The share is then an **upper bound**, and the point's `notes` say so. The first point is one.
4. **Small weeks are noisy.** A week with few commits, or a revert rate over a handful of commits, means little.
   - In the chart, the rates carry their counts ("k of n").
   - The band is `undecided` under 20 Ragon-made commits.
   - The weekly points may jump, and the eight-week window is what the ratchet reads.
5. **The spread.** The same change costs different numbers of tokens on different days: retries, longer contexts, a cold cache. No single week is evidence of a trend, and only a run of weeks is.
6. **What else it leaves out.** It does not measure the design work, the briefs, or the review effort that others spend on Ragon's diffs. The review effort is counted on the other side, which is fair to Ragon.
7. **Engine commits.** The commit and line shares count this repository only. The engine's tokens are in the token shares (open question 3).

## 11. Rollout phases

The phases have no dates. Each phase is entered only when its criteria hold. When the quality band fails (§6.4), routing steps back one phase for the kinds involved.

| Phase | Entry criteria | What happens |
|---|---|---|
| **0: instrumentation** | This spec is on `main` | Everything in §3–§7 is built: <ul><li>`--ragon-tokens`;</li><li>the land queue's refusal of a commit without it;</li><li>the job tag and the gate's usage log;</li><li>the coordinator's usage ledger covering every session;</li><li>`rbrb.jsonl`;</li><li>`scripts/rbrb.py` with its tests, the JSON, the chart, the README section and the workflow.</li></ul> From its entry, **every** landed commit carries `Ragon-Tokens`. Routing does not change yet. |
| **1: mechanical, docs, tests** | Two consecutive weeks in which every landed commit carried `Ragon-Tokens`, and in which the job-tagged Ragon tokens on the node are at least the sum of the trailers (the counters reconcile) | `mechanical`, `docs` and `tests` work is tried as a Ragon task first (§5). |
| **2: code with tests** | <ul><li>Each phase-1 kind meets the `task` tool's class gate: acceptance at least 95 % over at least 20 decided tasks, no revert and no shadow miss (`GATE_RATE`, `MIN_DECIDED`).</li><li>The quality band is `met` over the last eight weeks.</li></ul> | `code` work with a named failing-then-passing test goes to Ragon first. |
| **3: features behind the same gates** | <ul><li>The band is `met` for eight weeks with at least 20 Ragon-made `code` commits in them.</li><li>The default-flip reviewer said STOP on none of them.</li></ul> | A feature from a spec is split into tasks that each meet §5.2, and goes to Ragon first. Specs and the owner's decisions stay with the owner. |

## 13. Open questions (each with its default)

1. **Where the public token totals come from.** The weekly token counts and land counts come from private sources, so git history alone cannot hold them. **Default:** they are committed input rows in `docs/rbrb.json`, and `rbrb.py` derives everything else from git and those rows. There is no extra public file and no extra trailer.
2. **The workflow's credentials.** No workflow commits as a bot today, and the bots' keys never enter the repository. **Default:** the docs App's key is stored as an encrypted Actions secret, and the workflow mints an installation token from it. **Fallback, if the owner prefers no key on GitHub:** the coordinator's Monday timer makes the same commit through `as_team.py` and the land queue, and the workflow runs `rbrb.py --check` only.
3. **The engine repository in the commit share.** **Default:** no. The engine's tokens count (they are development tokens), and its commits are a separate history. They are reconsidered once the engine's commits carry the trailers too.
4. **The land-test failure rate in the ratchet.** **Default:** no. It is shown, but only the revert rate (and no bypass) decides the band, because a land-test failure was caught before `main`.
5. **The ratchet step `Δ`.** **Default:** 2 percentage points a week, capped by the four-week share (§6.1).
6. **Untagged interactive use of Ragon.** **Default:** excluded from `method_version` 1. It was in the hand-measured first point, and its `notes` say so.
